# v2 prospective protocol

SearchProtocol is written before native requests. Supply an agent-refined `--protocol` JSON containing problem, 1–3 candidate RQs/focal RQ, competing explanations, population/stage/setting/geography/period, constructs/outcomes/intervention, study types/language, eligibility and scope justification, keyword clusters/descriptors, British/American alternatives, seminal/contrary evidence and citation-chaining plan. Broad topics generate explicitly provisional dimensions, not invented facts about the user.

Preserve actual preparation time and amendments. On resumed/imported discovery use the original protocol; a timestamp created after the searches does not prove prospective search design. The engine logs exact executed queries/filters/IDs/counts/errors and screening/exclusions. Source access, actual scope coverage and method-quality judgements remain distinct from metadata enrichment and lexical ranking.


# Quantity intent and adaptive discovery (v3)

Before search persist the exact originating user quantity request, requested N, exact/at_least semantics, effective selection target and required deep-reading count. The agent maps clear English/Chinese quantity language to existing CLI flags and `--user-quantity-intent`; Python does not parse chat by implication. Explicit N overrides word count; otherwise ceil(words/100) has a floor of ten. Bare-topic/default and at-least requests are not capped at ten. A count below ten cannot bypass substantive ten-work minimum acceptance.

Native search retrieves broader candidates, tracks distinct IDs/deduplication and expands general/theory/recent/contrary queries if breadth is inadequate. `--search-candidate-budget` bounds feasibility and all expansion/stop decisions are logged. Candidate breadth is not actual full-text reading. Preserve original prospective protocol and actual archived observations on resume. If the user's count changes, record the amendment instead of rewriting the original request history.
